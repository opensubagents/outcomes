# examples/research-engineering

End-to-end example that consumes the
[`opensubagents/research-engineering`](https://github.com/opensubagents/research-engineering)
plugin and re-grades one of its frozen reports through the
[`open-outcome`](../../sdk-python/) Python SDK. The example asserts that
the per-dimension scores produced by the research-engineering plugin's
own `HeuristicGrader` and the Open Outcome SDK's `HeuristicVerifier`
**agree exactly** on the same input.

That parity assertion is what makes this directory valuable: it is the
runnable proof that the Open Outcome spec captures what the
research-engineering plugin already does, with no implementation drift.

## What's in here

| File | Purpose |
|---|---|
| `report.json` | A frozen `GeneratedReport` from the sibling plugin (May 2026 vendor-comparison brief). |
| `run.py` | Loads `report.json`, maps the brief to an Open Outcome `OutcomeDeclaration`, grades the report through both SDKs, asserts per-dimension parity, prints the OTel span attribute dict. |
| `outcome.json` | Generated by `run.py` — the brief in Open Outcome form, kept on disk as a CI fixture. |
| `verdict.json` | Generated by `run.py` — the verdict in Open Outcome form, kept on disk as a CI fixture. |
| `pyproject.toml` | Depends on `open-outcome` (path) and `research-engineering` (git). |
| `tests/test_end_to_end.py` | CI entry: runs `run.py`, asserts exit 0, asserts parity. |

## How to run it

```sh
cd examples/research-engineering
uv pip install -e .             # or: pip install -e .
python run.py
# expected: prints the OTel span attribute dict and a "parity: OK" line
```

`run.py` is intentionally readable end-to-end — it's the worked example
from [appendix D](../../specification/appendix-d-worked-example.md) of
the spec, in executable form.

## Why parity matters

The Open Outcome reference rubric (the five dimensions in
[appendix A](../../specification/appendix-a-rubric.md)) was lifted from
`research-engineering`'s rubric. If the two implementations of the rubric
ever disagree on the same input, exactly one of two things is true:

1. The spec or the SDK has drifted from the research-engineering grader
   (the rubric is the same in prose, but the implementations diverged).
2. The research-engineering plugin's grader changed and the spec needs to
   catch up.

Either way, this end-to-end is where it gets caught.
